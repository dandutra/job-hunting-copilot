`IngestScheduler` in `apps/api/src/ingestion/` ticks once an hour and hands each draft to `matchSighting`.

- An adapter declares `minIntervalMs` (default one hour). The scheduler skips it until that long after `ingest_cursor.last_attempt_at`, which is written after every attempt, failed or not. A failing slow adapter is therefore retried at its own rate, not every tick. `last_poll_at` keeps its old meaning (the last poll with no `blocked` or `fault` error) and is empty until the first good poll. If the cursor write itself fails, the poll is reported `failed` and alerts, even when every draft matched. The adapter then runs again on the next tick, because `last_attempt_at` was not written either. The check allows 60 seconds of tick jitter, so an hourly adapter is not skipped for a tick that arrives a few milliseconds early.
- Board adapters (one request per Watched company) ignore `since`, tag each error with `watchedCompanyId` and list every board in `AdapterResult.boards`. One board's error never stops the others, and their drafts still reach the matcher. The scheduler, not the adapter, alerts for board errors, naming the Company. A board error with `httpStatus` 404 alerts at most once per 24 hours per board, counted from the last alert that was delivered. That memory lives in the process, so a restart can repeat one alert.
- `PollWindow.shouldStop()` turns true when the drain starts. A board adapter checks it between requests and returns what it has. A board cut off this way is reported `incomplete`, which is neither an error nor a full read, so it must never be used as evidence that a Posting left the board.

- `AdapterResult.completeBoards` lists the Watched company ids whose board was read in full with no error. After matching, the scheduler closes each such board's open Sightings (`watchedCompanyId` set, `closedAt` empty) whose listing key is not in this read and whose `lastSeenAt` is more than 24 hours old, so one bad page cannot close a job. A board with no draft in its read never closes anything, because Workday pages wrap and any board can return a bad page. The exception is a board whose `BoardReport.rows` is above zero: it listed jobs, all outside the Search area, so its open Sightings close as usual. A board adapter leaves a board out of `completeBoards` when any of its rows was a `bad-row`, because that row may still be listed. A row with no location is a `bad-row` too, because a lost location field would make every row look out of area and close the whole board. A board that keeps one bad row is therefore never complete, and its gone jobs go Stale, not Closed. The Workday adapter first asks the detail call for the location, because Thomson Reuters never sends one in the list, and the row is a `bad-row` only when the detail has none either. If it still has open Sightings, the scheduler adds a `fault` to the outcome. That fault carries no `watchedCompanyId`, so it logs but does not alert, and it holds the window back. The JobSpy adapter returns an empty list. The matcher clears `closedAt` when it refreshes a Sighting inside the 30-day key window, and a closed Sighting older than that starts a new one. `postingState` in `apps/api/src/matching/posting-state.ts` derives open, closed or stale on every read.
- The advisory lock (`pg_try_advisory_lock`) lives on a `pg` client opened for each tick, not on Prisma. A pooled connection can change between queries, so a lock taken through Prisma could be released early or never. Ending the client drops the lock. The lock also stops two `ingest` containers from polling together during a deploy.
- The lock client needs an `error` listener: if its idle socket dies mid-poll, `pg` emits `error`, and with no listener the process crashes. The poll in progress then finishes without the lock, which is safe because the matcher has its own lock and a rerun adds nothing.
- The drain runs in `onModuleDestroy`, because `PrismaService` disconnects in its own `onModuleDestroy`. A later hook such as `beforeApplicationShutdown` would find the database already closed. The Nest-level test in `ingest-scheduler.spec.ts` covers this order.
- A window advances (the `ingest_cursor` row) only after a poll with no `blocked` or `fault` error. A draft that fails to match is a `fault` unless the matcher rejects it. A `bad-row` error does not hold it back, because asking again returns the same row. A draft the matcher rejects with `BadRequestException` also counts as a bad row. An example is a company named "Canada", which `normalizeName` strips to nothing. The next window starts 2 hours before the last good poll, defaults to 24 hours with no cursor, and never reaches back more than 7 days.
- Rerunning an adapter is safe because `matchSighting` updates the Sighting it already holds for a source and listing key. A crash mid-batch leaves some drafts matched and the cursor unmoved, and the rerun fills in the rest.
- The JobSpy adapter sends one request per poll, with a 5-minute client timeout, so a poll in progress fits inside the 6-minute `stop_grace_period`. A second search term per adapter would break that, so the search comes from `JOBSPY_SEARCH_TERM` and `JOBSPY_LOCATION`, one pair for both boards, capped at `JOBSPY_RESULTS_WANTED` rows. `deploy/compose.prod.yaml` must list each of these under `x-app-env`, because `--env-file` only feeds interpolation and never reaches the container. A blank value means the default, and a bad results count stops `ingest` at startup. `JOBSPY_LOCATION` defaults to "Toronto, ON", and the adapter still drops every returned row that `inSearchArea` rejects, because JobSpy's location search matches a radius, not the exact city. A row with `is_remote` set is judged as "remote" plus its location, since JobSpy often reports remote jobs as just "Canada". Beside "remote", `inSearchArea` accepts "worldwide" or "global" and reads "CAN" and "ON" as Canada and Ontario. Those two codes are also English words, so they count only where a place code sits, with a separator or the string edge on both sides. A dash counts as a separator only when it is spaced or joins two codes ("CAN-ON-Remote"), so "Remote - Ottawa, ON" is in, and "Remote, On-site, Austin, TX" and "Remote or On-site" stay out. Any other word keeps the row out, so "Remote - EMEA" and "Remote, CA" (California) are dropped. A city name alone matches, so "Aurora, CO" passes.
- `/scrape` has no paging. A window with more listings than `JOBSPY_RESULTS_WANTED` loses the rest, and the poll still counts as `ok`. Holding the cursor back would not help, because the same request returns the same capped rows.
- A JobSpy row with a description is `full`, and one without is `none`. JobSpy never returns a snippet, and LinkedIn rows have no description while `linkedin_fetch_description` is off.
- `pollFinished` logs each outcome and then pings `HEARTBEAT_URL` unless every adapter that ran ended `failed`. A poll where all adapters were `skipped` as not yet due still pings. Without that, a restart in the second half of the hour skips every adapter on its boot poll, and the next ping comes more than 90 minutes after the last one, past the check's grace. A ping error is logged and never fails the poll. See [Deploy](../runbooks/deploy.md#what-each-alert-means). The alert hook is log-only. The adapter calls the alert hook itself, so a fault raised inside an adapter alerts once, and one that escapes an adapter is alerted by the scheduler.
