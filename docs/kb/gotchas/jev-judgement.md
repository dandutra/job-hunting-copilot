`apps/api/src/jev/` asks Jev one request per Posting and stores the raw answers in `jev_judgement`. Rows are never updated or deleted, and the newest row per Posting is live.

- The runner keeps no queue. After every poll it reads the tables and judges a Posting that is open, was posted in the last 14 days, and either has no judgement, was last judged on a snippet or nothing and is now full, or was last judged on an older profile version. The window applies to all three reasons. A Closed or Stale Posting with no judgement is never judged. Due Postings run newest `postedAt` first, then highest ID.
- The Title filter (`titlePasses` in `apps/api/src/jev/title-filter.ts`) keeps a Posting out of Jev by its title, and the ingest scheduler applies it too (see [Ingest scheduler](ingest-scheduler.md)). It reads `config/title-filter.json` once per process, because `getTitleFilter()` caches it, so a list change needs a restart of `ingest`, and of the API too, because the API reads the file on its first feed request and caches it (see the `entryLevel` list below). A deploy restarts both. The same file holds `searchTerms` for the JobSpy adapter, read once per process too through `getSearchTerms()`. A term keeps its case and trimmed text, must be a non-blank string in a non-empty list, and must not contain a double quote, because the adapter wraps each term in quotes. The ingest module builds both JobSpy adapters at startup, so a bad list stops `ingest` before the first tick. The API process never reads the search terms, only the lists. `lead` and `architect` are left out on purpose. The exempt phrase "Member of Technical Staff" is removed before the exclude check only, because AI labs use it at every level. It is also an include phrase, so stripping it before the include check would fail "Member of Technical Staff, Agent Code". The user found 32 open Postings with it in the production sample on 2026-11-19. Another word in the title, such as Senior, still filters it. Matching lowercases every entry and title and splits on any run of non-letters and non-digits (Unicode-aware), and validation does not warn about symbols. An entry such as "C++ developer" loads as "c developer", and "C#" as "c", so the entry quietly widens. The path `../../config/title-filter.json` is relative to the cwd, which is `apps/api` for jest, `dev:ingest`, `tier:recompute`, `jev:sample` and the production image (WORKDIR `/repo/apps/api`, config copied to `/repo/config`). `main.ingest.ts` calls `getTitleFilter()` before Nest starts, so a missing file, invalid JSON, an empty `include`, a missing list or a blank or non-string entry stops `ingest` with a message starting "title filter:". Checked on 2026-11-20: with the file moved away, `node dist/main.ingest.js` exited 1 with "title filter: cannot read ../../config/title-filter.json (ENOENT ...)". The runner never judges a filtered Posting, not even through `postingIds`. `RunCounts` and the run log carry `filtered`, counted among the Postings in the window or the sample, not only the otherwise-due ones, so it shows what the filter removed.
- The same file holds a third list, `entryLevel` (13 phrases: junior, jr, new grad, new graduate, recent graduate, graduate, entry level, early career, campus, undergraduate, associate, apprentice, trainee), required and non-empty like `include`. `entryLevel(title)` is true on an `entryLevel` phrase as whole words, or on a level-number token `i` or `1` unless the next word is year, years, month, months or yr. It is display-only: unlike `include` and `exclude` it never drops a row, and it feeds the feed's `entryLevel` flag (see [Feed and Posting detail](feed-and-posting-detail.md)). The API process reads the file for it on the first feed request and caches it, so a list change needs an API restart as well as an `ingest` restart. `main.ts` does not call `getTitleFilter()` at startup, unlike `main.ingest.ts`, so a bad file shows as a 500 on `GET /postings` and `GET /postings/:id`, not as a boot failure. Production cannot ship a bad file, because the committed-config spec gates the deploy.
- Known false positives of the level-number rule, not fixed. It checks only the next word, so a year range ("1-3 years" becomes `1 3 years`) and "yrs" are flagged. Punctuation splits give "I/O Systems" and "I.T. Developer" a bare `i`, and "Tier 1 Production Support" is flagged. "new graduate" and "recent graduate" are redundant with "graduate", and stay because the ticket's confirmed list names them.
- At most 150 calls run in any 24 hours. A call counts when it stored a `jev_judgement` or a `jev_failure` row, so a call that stored nothing (the process died mid-call, or Jev was down) is not counted. `DAILY_CALL_CAP` sits beside `RUN_BUDGET_MS`. A profile import reaches the whole window over a day or more, and the run log's `capped` is what waited. #33 must leave candidate judgements out of this count, or they use up the cap.
- A Posting whose description turns full after it leaves the 14-day window stays judged on its snippet. The decision accepts that.
- A failure that is the Posting's fault (an `invalid` answer, or HTTP 400, 413 or 422) stores a `jev_failure` row with the kind and status and no message. Three rows and the Posting is no longer due, and nothing clears them. Any other failure ends the run for that poll and stores nothing: 429 or 529 after the client's retries, any 5xx, a network error, a `malformed` reply with no `model`, and every other 4xx. That last group covers a revoked key (401, 403), a used-up quota (402) and a retired model pin (404). The ticket first counted every 4xx but 429 as the Posting's fault, and a revoked key would then have retired the newest Postings about 50 a day. An outage, or a bad key, costs one call per poll.
- Known limits of the failure rules, not yet ticketed. A request-wide 400, 413 or 422 or an `invalid` answer (from the profile summary or the question set) still stores a failure on every call, and retires about 50 Postings a day because nothing clears `jev_failure`. A merge moves the absorbed Posting's failure rows, so a survivor can inherit up to 3 and stop being due. A reply with `model` but no `answers` counts as `invalid`, the Posting's fault, not `malformed`. `deploy/restore-drill.sh` `DRILL_TABLES` does not list `jev_failure`.
- `run({ postingIds })`, used by `jev:sample`, judges exactly those Postings and skips the window, the open check and the cap, but not the Title filter. It still stops on a Jev outage and respects the three-failure limit.
- A Posting with no judgement has no Tier. Never default it to C. The ingest process recomputes Tiers after each Jev run (see `tier-scoring.md`), so a new judgement gets its Tier in the same poll.
- A new question set version does not rejudge by itself. Bump `QUESTION_SET_VERSION` when any wording changes, and decide then whether to rerun.
- The model is pinned to `jev-1.14.0` and the client refuses an alias such as `jev-latest`. The stored `model` is the one Jev returned.
- Only 429 and 529 retry inside a call (three times, with backoff). The SDK also retries timeouts and dropped connections by default, so the client turns both off; a 500, a timeout or a dropped connection waits for the next poll.
- The batch runs inside the ingest lock, after the heartbeat. It stops between Postings on shutdown or after 20 minutes, so the lock frees before the next tick and a deploy's drain fits the 6-minute stop grace. The 150-call cap, not the budget, is what usually bounds a run.
- After a merge, the surviving Posting's newest row may be the absorbed Posting's judgement, made on the other text. It is not rerun unless the description moves to full or the profile changes.
- The SDK log is off, and the runner logs only a Posting ID and an HTTP status. An SDK error message and a Jev error body can quote the request, which holds the profile summary.
- `TYPESAFE_API_KEY` empty means nothing is judged and the ingest process logs one warning at boot.
- A merge moves judgements and `jev_failure` rows to the surviving Posting, like Tailored resumes. Failure rows feed the daily cap and the three-failure limit, so the cascade must never be what removes them.
- The Noul thresholds that turn a probability into "the text states it" live in `config/tier-config.json` as `capThresholds`, not in the question set. `outside_gta` is 0.5; the others keep TypeSafe's suggested 0.7, unchecked against real text. The key `outside_gta` now means outside the Search area. Its question names the Greater Toronto Area, London (Ontario) and Halifax (Nova Scotia), and `QUESTION_SET_VERSION` is "2". The key kept its name because a rename reaches `tier-config.json`, `feed.dto.ts`, `openapi.json`, `schema.d.ts` and `format.ts` for no change in behaviour. The web label is "Work outside the Search area". The 0.5 threshold below was set on the old wording and is unchecked on the new one, so the Jev regression rerun (#33) must run before trusting it. The first real run (2026-11-10, 10 local Postings with full descriptions, `pnpm --filter api jev:sample`) says 0.7 is too high for `outside_gta`. Lachine scored 0.76, but Vancouver, Greater Sudbury and Brantford scored 0.52 to 0.57, while every GTA or remote Posting scored 0.11 or less. A cut at 0.5 separated all ten. `closed_to_juniors` came out 0.86 to 0.92 for "3+ years" and "four years", 0.75 for a Senior title and 0.61 for "5+ years". So it ranks years inconsistently, and whether "3+ years" counts as closed to juniors is a product decision, not a threshold.
- `jev:sample` imports `data/master-profile.yaml` into the local database and sends its fit summary to TypeSafe. Each call used about 4,500 to 5,400 input tokens. It picks the lowest-ID unjudged Postings with a full description after dropping filtered titles, because a filtered Posting never gets a judgement and would otherwise fill every sample. It prints the count it dropped as `filtered`.
