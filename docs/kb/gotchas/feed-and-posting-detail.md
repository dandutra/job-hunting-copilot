The API is in `apps/api/src/feed/`. The screen is in `apps/web/src/feed/`, mounted by `App.tsx` as one layout route over `/` and `/postings/:id`, so selecting a Posting changes the URL without remounting the list.
- `GET /postings` returns a flat array, already ordered Tier A, B, C and then newest Posted at (ties by id). The screen groups it. A Posting with no `posting_tier` row is left out, because it has no group, so a Posting is invisible until the next ingest poll recomputes Tiers after its judgement (within the hour). `GET /postings/:id` still answers for it, with `tier: null`.
- `include=closed` adds Closed and Stale Postings, each with a `state`. Any other value is a 400. The screen puts them in one "Closed and stale" group, not in their Tier group. State is derived on each read with `postingState`.
- The row flag "Capped" and the full cap reason both come from `capsApplied`. The web app turns the cap names into words in `format.ts`, so a new cap in `question-set.ts` shows as its raw name until that map gets an entry.
- The detail's "Why" is computed per request from the judgement the Tier row points at and the config file as it is now (`tierBreakdown`). If someone edits `config/tier-config.json` and does not run `tier:recompute`, the points can disagree with the stored Tier. The detail then sets `why.stale` (the file's hash differs from `posting_tier.config_version`) and the screen says so. The API image carries its own copy of the file, so a seed run on the Mac also needs a deploy. If the file cannot be read, or the stored answers no longer validate, `why`, `roleFamily` and `workArrangement` are null and the rest still answers.
- The API image now copies `config/` to `/repo/config`, and the feed reads `../../config/tier-config.json` from `apps/api` (or `TIER_CONFIG_PATH`). The Label queue schedule stayed a constant for the opposite reason.
- Sightings with one URL come back as one `links` entry listing every Job source, in Sighting order.
- A Lookalike shows on both Postings of the pair. The hint's Merge calls `POST /lookalikes/:id/merge` and opens the surviving (lower id) Posting. "Not the same" calls `/dismiss`. The screen hides the hint at once and reloads the list.
- The Feed correction API only appends, so "toggles off on a second click" clears the mark in the browser and sends nothing. A reload shows the stored correction again. A real undo needs its own endpoint.
- "Last 3 days" filters in the browser, on `postedAt` within 72 hours of the moment the box was ticked (a render may not read the clock under the `react-hooks/purity` lint), across every group including "Closed and stale". `postedAt` is the earliest board date among the Posting's Sightings, or the first-seen time when the board gives none. An Ashby republish resets `publishedAt` but does not move a Posting the app has already seen ([Ashby](../job-sources/ashby.md)), so an old Ashby job passes only when the app first sees it after a republish, or when it comes back after 30 days unseen. The span is a constant in `FeedScreen.tsx`.
- `j` and `k` move through the Postings in groups that are open, and ignore typing in a field. `/postings/:id` for a Posting the list does not show (a collapsed Tier, a Closed Posting) still opens its detail.
- `GET /postings` and `GET /postings/:id` carry `metros`: every Search-area place the location text names (`gta`, `london-on`, `halifax`, `remote-canada`), never `other`. It is empty for text outside the area. A Posting that names several places carries several and shows under each. `metrosOf` (`apps/api/src/matching/metro.ts`) judges each ";" entry alone, and `remote-canada` means an entry in the area that names none of GTA, London or Halifax (`inRemoteCanada` in `search-area.ts`), so "Remote - Toronto, ON" is `gta` only. The merge rule's `metroOf` is the first of `metrosOf` or `other`, so the filter and the merge rule cannot disagree (see [Text merges and Lookalikes](text-matching.md)).
- The Location select filters in the browser on `metros`, before the 3-day cutoff and the group collapse. So `j` and `k` walk only what is left, and a Posting opened by URL still opens when the filter hides it. The options are a fixed list in `format.ts` (labels only, no place rules in the web app), so a new Search-area place needs an entry there. There are two empty messages: "No Postings in this location." when the place has none, and "No Postings in the last 3 days." when the place has some and the cutoff removes them. The choice is not kept across a reload and is not in the URL.
- A focused `<select>` swallows `j` and `k` (`typing()` ignores selects), so the screen blurs it on change. A browser that fires `change` per arrow key (Firefox, Chrome on Windows and Linux) loses focus after the first step. macOS Chrome and Safari open the popup instead, so check a keyboard change of the filter in more than one browser.
- Live check of #138 (dev API and web dev server, not the ingest poller that `pnpm dev` also starts, because it polls real boards and writes to the dev database): 92 Postings, 85 GTA (3 of them also name remote), 5 remote-canada, 0 London or Halifax, 5 outside the area. London and Halifax stay empty until ingest stores such Postings after #136. A reload collapses Tier C again, so a script must open it before counting.
- The screens read the API client from `useApi()` (`ApiProvider` in `main.tsx`). A test passes a stub client with `GET` and `POST`.
