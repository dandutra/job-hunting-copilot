`WorkdayAdapter` reads each Workday Watched company every 3 hours (`minIntervalMs`). It polls one tenant at a time and sends each request 1.5 s after the last, across tenants too. The research is in `docs/research/workday-json-endpoint.md` on the `research/workday-json-endpoint` branch.

- The Watched company's slug is `tenant.wdN/site`, for example `rbc.wd3/RBCGLOBAL1`, and the seed takes it from the row's URL, not from the CSV slug column. A wrong `wdN` answers 422, which is a `fault` on that board. A 429 or 403 is `blocked`.
- The list call is a POST with `limit: 20`, the most Workday accepts (21 returns 400). Page one alone has `total` and `facets`, and later pages report `total: 0`. An offset at or past `total` returns page one again, so the walk stops at `offset >= total` and dedupes by path.
- If a facet holds a value named "Canada" (at any nesting depth), the adapter applies it to the rest of the walk. A facet whose name has "country" in it wins (`Country`, `Location_Country`, `locationCountry`, and Salesforce's long custom name). Page one is unfiltered, so the filtered walk restarts at offset 0. Otherwise it would skip rows that the filter puts on page one. The filtered page one gives its own `total`, and the walk ends there. That total must not be above the unfiltered `total` or below the Canada value's own `count`, and a Canada value with no `count` fails the check. If any test fails, the walk ends at the unfiltered total and the tenant is not complete, because an early end would close every job the walk missed. In the 2026-11-09 live run, Nvidia, Salesforce and Workday had few Canada jobs, so the filter saved most of their calls.
- Nvidia has no country facet and files Canada under `locationHierarchy1`, so any facet with a "Canada" value is the fallback. A single location record can also be named "Canada", so the fallback takes the value with the largest `count`. A fallback filter still ends the walk early, but it never makes a tenant complete. Only a country facet is sure to cover every Canadian job. Nvidia's gone jobs therefore go Stale, not Closed. RBC's site had no Canada facet of any kind on 2026-11-09, so RBC is walked unfiltered, about 40 list calls.
- The list has only a relative `postedOn` label. The detail call (`GET .../wday/cxs/{tenant}/{site}{externalPath}`) gives `startDate` (a day, used as the date), `jobDescription` (HTML, stored as `full`) and `location` plus `additionalLocations`.
- The key is `workday:{tenant}:{requisition}`, where the requisition is the token after the last `_` of the path. The path slug keeps the title from the first posting, so it cannot be the key.
- Thomson Reuters sends no `locationsText` on any row. A row without one is judged by its detail call, like an "N Locations" row.
- A row whose `locationsText` is "N Locations" cannot be judged from the list. It costs one detail call, and a row judged out of the area goes into an in-memory set, so it costs none until the process restarts. A single-place row outside the area is dropped without a call. A row in the area with no stored Sighting for its key gets the detail call. A known key reuses the stored Sighting's fields and only refreshes last-seen, so a "3 Locations" row that is already stored is not judged again. The title still comes from the list row, because Workday retitles a listed job and the path slug keeps the old title. A key counts as known only when its Sighting was seen in the matcher's 30-day window. The scheduler passes the same `now` to the adapter and the matcher, so the two windows agree. A repost after 30 quiet days starts a new Posting, so it gets a fresh detail call, with a fresh date.
- `shouldStop()` is checked before every request. A tenant cut off by it is `incomplete` and not an error, and its drafts so far still go to the matcher.
- A tenant is in `completeBoards` only when every page came back clean and no row was a `bad-row`. A failed detail call on one row is a `bad-row`, which keeps the tenant incomplete. A detail 403 with `errorCode` S22 is a listing that closed after the list call. That makes it a `bad-row`, not `blocked`. Any other 403 on a detail call blocks the tenant. S22 comes from another crawler's code and has not been seen here. A tenant whose walk `total` (the filtered one when Canada applies) is 2000 or more is never complete. Nvidia's unfiltered query reports exactly 2000, which is the cap, not a count, because some tenants refuse to page past 2000. The walk reads at most 2000 rows, and a warning is logged. Filtering on Canada keeps every seeded tenant under the cap.
- The poll cost is large: RBC has about 850 Postings, so a cold pass is about 43 list calls plus a detail call per in-area row, at 1.5 s each. Later polls only call the list pages. The 3-hour rate follows from that.
- Workday sends no rate-limit headers and sits behind Cloudflare. Other crawlers saw synchronized 429 and 303 bursts across many tenants.
- RBC's robots.txt has `Disallow: /RBCGLOBAL1/` for all agents. That path is the HTML career site, not `/wday/cxs/rbc/RBCGLOBAL1/`, but the intent is plain. RBC is polled anyway, and this is an accepted ToS risk.
- A live run on 2026-11-09 polled all 19 verified tenants: 359 requests, every one a 200, no 429, in 14 minutes, with most rows treated as already stored. TMX reports `total` on every page, not only page one. Single rows with no `externalPath` (RBC, Sun Life) or no location (Manulife) appeared once and were gone on a re-read, which kept those tenants incomplete for that poll. The fixtures are still trimmed from the research samples.
